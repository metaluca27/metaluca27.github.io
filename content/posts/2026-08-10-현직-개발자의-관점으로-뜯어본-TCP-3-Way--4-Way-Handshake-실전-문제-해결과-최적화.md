"네트워크의 기본은 TCP/IP, TCP/IP의 기본은 3-Way Handshake와 4-Way Handshake"라는 말, 개발자라면 한 번쯤 들어보셨을 겁니다. 저 역시 그랬죠. 하지만 처음에는 그저 교과서적인 설명으로만 이해하고 넘어갔습니다. 그러다 작년 여름, 저희 백엔드 서비스의 특정 API에서 `Connection timed out` 에러가 간헐적으로 발생하고, 서버의 리소스 사용량이 비정상적으로 치솟는 문제를 겪으면서 이 두 가지 핸드셰이크 과정이 얼마나 중요한지 몸소 깨달았습니다. 단순히 이론만 아는 것이 아니라, 실제 서비스에서 어떤 문제를 일으킬 수 있고 어떻게 해결해야 하는지 직접 경험하며 배웠던 내용들을 여러분과 공유하고자 합니다.

## TCP 3-Way Handshake: 안전한 연결의 시작

TCP (Transmission Control Protocol)는 신뢰할 수 있는 데이터 전송을 보장하기 위해 연결을 설정하고 해제하는 복잡한 과정을 거칩니다. 그 시작이 바로 3-Way Handshake입니다. 클라이언트와 서버 간에 데이터를 주고받기 전에 서로 통신할 준비가 되었는지 확인하는 과정이죠.

제가 처음 이 과정을 깊이 들여다본 건, 신규 마이크로서비스를 배포하고 외부 API와의 연동 테스트를 할 때였습니다. 특정 상황에서 클라이언트(저희 서비스)가 외부 API 서버에 연결하는 데 실패하고, 로그에 `connect() failed: Connection timed out`이라는 메시지가 수십 건씩 찍히는 것을 확인했어요. 이때 `tcpdump`를 이용해 실제 패킷을 캡처해보면서 3-Way Handshake가 어떻게 작동하는지, 그리고 어디에서 문제가 생기는지 시각적으로 파악할 수 있었습니다.

### 3-Way Handshake 작동 과정

1.  **SYN (Synchronize Sequence Number)**: 클라이언트가 서버에 연결을 요청합니다. "나 너랑 통신하고 싶어! 내 초기 시퀀스 번호는 X야."
2.  **SYN-ACK (Synchronize-Acknowledgement)**: 서버는 클라이언트의 요청을 받고, 연결을 수락한다는 응답과 함께 자신의 초기 시퀀스 번호를 보냅니다. "알았어! 나도 너랑 통신할게. 너의 X를 잘 받았고, 내 초기 시퀀스 번호는 Y야."
3.  **ACK (Acknowledgement)**: 클라이언트는 서버의 응답을 받고, 연결이 성공적으로 수립되었음을 알립니다. "응, 너의 Y도 잘 받았어! 이제 데이터를 보낼 준비가 됐어!"

이 세 단계를 거쳐 클라이언트와 서버는 서로의 존재를 확인하고, 데이터 전송에 사용할 초기 시퀀스 번호를 동기화하며, 통신할 준비를 마칩니다.

### 실전: `tcpdump`로 3-Way Handshake 엿보기

실제 서버에서 `tcpdump` 명령어를 사용하면 이 과정을 눈으로 확인할 수 있습니다. 예를 들어, `192.168.1.10`에서 `192.168.1.20`의 80번 포트에 연결을 시도할 때 다음과 같이 캡처할 수 있습니다.

```bash
# 서버 (192.168.1.20)에서 80번 포트로 들어오는 트래픽 캡처
sudo tcpdump -i eth0 'port 80 and host 192.168.1.10' -n -vvv

# 클라이언트 (192.168.1.10)에서 서버의 80번 포트로 연결 시도
# curl 192.168.1.20:80 또는 telnet 192.168.1.20 80
```

`tcpdump` 출력 예시:

```
00:00:00.000000 IP 192.168.1.10.54321 > 192.168.1.20.80: Flags [S], seq 12345, win 29200, options [mss 1460,sackOK,TS val 1234567,ecr 0], length 0
    # [S]는 SYN 플래그, 클라이언트가 54321번 포트에서 80번 포트로 연결 요청

00:00:00.000123 IP 192.168.1.20.80 > 192.168.1.10.54321: Flags [S.], seq 67890, ack 12346, win 28960, options [mss 1460,sackOK,TS val 7654321,ecr 1234567], length 0
    # [S.]는 SYN-ACK 플래그, 서버가 클라이언트의 SYN을 ACK하고 자신의 SYN을 보냄

00:00:00.000210 IP 192.168.1.10.54321 > 192.168.1.20.80: Flags [.], ack 67891, win 29200, options [mss 1460,sackOK,TS val 1234568,ecr 7654321], length 0
    # [.]는 ACK 플래그, 클라이언트가 서버의 SYN-ACK를 ACK하며 연결 수립 완료
```
이 캡처를 보면, 약 0.2ms 만에 3-Way Handshake가 완료되었음을 알 수 있습니다. 실제 서비스에서는 이 시간이 네트워크 지연이나 서버 부하에 따라 달라질 수 있죠. 제가 겪었던 `Connection timed out` 문제는 SYN 패킷이 서버에 도달하지 못하거나, 서버가 SYN-ACK를 보냈음에도 클라이언트가 받지 못하는 경우였습니다. 결국 방화벽 설정 오류와 로드 밸런서의 비정상적인 헬스 체크 문제로 밝혀졌습니다.

## TCP 4-Way Handshake: 우아한 연결 종료

연결 설정만큼 중요한 것이 바로 연결 종료입니다. TCP는 4-Way Handshake를 통해 양방향 통신이 완전히 종료되었음을 보장합니다. 일방적으로 연결을 끊는 것이 아니라, 양측 모두 더 이상 보낼 데이터가 없음을 확인하고 안전하게 리소스를 해제하는 과정이죠.

저희 서비스에서 4-Way Handshake의 중요성을 실감한 건, 트래픽이 몰리는 시간대에 서버의 `TIME_WAIT` 상태 커넥션이 급증하고, 이로 인해 새로운 연결 생성이 지연되거나 `Address already in use` 에러가 발생하는 경험을 했을 때입니다. 특히 웹훅 서비스처럼 짧은 시간에 수많은 아웃바운드 연결을 생성하고 종료하는 경우에 이 문제가 두드러집니다.

### 4-Way Handshake 작동 과정

1.  **FIN (Finish)**: 연결을 먼저 종료하고 싶은 측(클라이언트 또는 서버)이 상대방에게 FIN 패킷을 보냅니다. "나 이제 더 이상 보낼 데이터 없어. 연결 끊고 싶어."
2.  **ACK (Acknowledgement)**: 상대방은 FIN 패킷을 받고 ACK 패킷을 보냅니다. 이 ACK를 받은 쪽은 이제 `FIN_WAIT_2` 상태가 됩니다. "알았어. 네 종료 요청 잘 받았어. 근데 나는 아직 보낼 데이터가 있을 수도 있어."
3.  **FIN (Finish)**: 데이터 전송을 마친 상대방 역시 FIN 패킷을 보냅니다. "나도 이제 보낼 데이터 없어. 나도 연결 끊고 싶어."
4.  **ACK (Acknowledgement)**: 최초 종료 요청을 보냈던 측이 최종 ACK 패킷을 보내 연결을 완전히 닫습니다. 이 ACK를 보낸 측은 `TIME_WAIT` 상태로 일정 시간 대기 후 소켓을 닫습니다. "응, 너의 FIN도 잘 받았어! 이제 진짜 끝이야."

이 과정을 통해 양쪽 모두 더 이상 전송할 데이터가 없음을 확인하고, 모든 데이터가 전달되었음을 보장하면서 소켓 리소스를 안전하게 해제합니다.

### 실전: `netstat`으로 `TIME_WAIT` 상태 확인하기

`netstat` 또는 `ss` 명령어를 사용하면 현재 시스템의 TCP 연결 상태를 확인할 수 있습니다. 특히 `TIME_WAIT` 상태의 커넥션 수를 모니터링하는 것이 중요합니다.

```bash
# 현재 시스템의 모든 TCP 연결 상태와 프로세스 정보 확인
netstat -natp | grep TIME_WAIT | wc -l

# 더 빠르고 상세한 ss 명령어 (소켓 통계)
ss -t state time-wait | wc -l
```

`netstat` 또는 `ss` 출력 예시:

```
# netstat -natp (일부 발췌)
tcp        0      0 192.168.1.20:443        10.0.0.5:54321          TIME_WAIT   -
tcp        0      0 192.168.1.20:443        10.0.0.6:54322          TIME_WAIT   -
... (수백, 수천 라인)
```

제가 겪었던 상황에서는 이 `TIME_WAIT` 상태 커넥션이 평소 500개 수준에서 특정 이벤트 발생 시 순식간에 15,000개 이상으로 치솟았습니다. 이로 인해 시스템의 ephemeral port(임시 포트)가 고갈되어 새로운 아웃바운드 연결을 맺지 못하는 상황에 처했죠. 이 문제를 해결하기 위해 Linux 커널 파라미터 튜닝을 진행했습니다.

## 3-Way Handshake vs 4-Way Handshake 비교

두 핸드셰이크 과정은 목적과 패킷 교환 방식에서 분명한 차이를 보입니다. 아래 표는 제가 중요하게 생각하는 핵심 차이점을 정리한 것입니다.

| 특징          | TCP 3-Way Handshake                  | TCP 4-Way Handshake                      |
| :------------ | :----------------------------------- | :--------------------------------------- |
| **목적**      | 신뢰할 수 있는 연결 설정             | 신뢰할 수 있는 연결 종료                 |
| **방향**      | 단방향 요청, 양방향 확인             | 양방향 종료 요청 및 확인                 |
| **패킷 수**   | 최소 3개 (SYN, SYN-ACK, ACK)         | 최소 4개 (FIN, ACK, FIN, ACK)            |
| **상태 변화** | CLOSED -> SYN_SENT -> ESTABLISHED    | ESTABLISHED -> FIN_WAIT_1 -> FIN_WAIT_2 -> TIME_WAIT -> CLOSED |
| **주요 이슈** | 연결 지연, SYN Flooding 공격         | TIME_WAIT 포트 고갈, 자원 누수           |

## 제가 직접 겪은 시행착오와 깨달음: `TIME_WAIT` 폭증과 해결

앞서 언급했듯이, 저희 서비스에서 `TIME_WAIT` 커넥션이 폭증하여 문제가 발생했습니다. 특히 고성능 웹 서버나 API 게이트웨이처럼 수많은 클라이언트 연결을 처리하거나, 저희처럼 잦은 아웃바운드 연결을 맺고 끊는 서비스에서 빈번하게 발생하는 문제입니다.

**문제 발생 시점:**
특정 시간대에 트래픽이 평소보다 약 3배 증가하면서, `netstat -natp | grep TIME_WAIT | wc -l` 명령어로 확인한 `TIME_WAIT` 상태의 연결이 1분 만에 2000개에서 18000개 이상으로 치솟았습니다. 동시에 저희 서비스는 외부 API로의 요청에서 `java.net.BindException: Address already in use` 에러를 뿜어내기 시작했습니다. 이는 ephemeral port가 고갈되어 새로운 소켓을 열 수 없다는 의미입니다.

**원인 분석:**
기본적으로 TCP 연결이 닫힐 때 `TIME_WAIT` 상태는 일정 시간 (보통 60초) 유지됩니다. 이는 네트워크에 남아있는 지연된 패킷들이 새로운 연결에 영향을 주지 않도록 하기 위함입니다. 그런데 고빈도 연결/해제가 반복되면, 이 `TIME_WAIT` 상태의 연결들이 쌓여 시스템이 사용할 수 있는 포트(일반적으로 32768~61000)를 모두 점유하게 됩니다.

**해결 과정:**
저는 다음과 같은 리눅스 커널 파라미터 튜닝을 통해 이 문제를 해결했습니다.

1.  **`net.ipv4.tcp_tw_reuse` 활성화**: `TIME_WAIT` 상태의 소켓을 새로운 아웃바운드 연결에 재사용할 수 있도록 합니다. 다만, 이는 클라이언트 측(연결을 시작하는 측)에서만 효과가 있습니다.
2.  **`net.ipv4.tcp_tw_recycle` 비활성화 (권장)**: 이 옵션은 `TIME_WAIT` 소켓을 더 빠르게 재활용하지만, NAT 환경에서 문제가 발생할 소지가 있어 대부분의 경우 비활성화하는 것이 권장됩니다. 저 역시 문제를 겪어 비활성화했습니다.
3.  **`net.ipv4.tcp_fin_timeout` 단축**: `FIN_WAIT_2` 상태에서 대기하는 시간을 줄여 `TIME_WAIT` 상태로 더 빠르게 전환되게 합니다. 기본값은 60초입니다.

**적용 명령어:**

```bash
# /etc/sysctl.conf 파일 수정
sudo vi /etc/sysctl.conf
```

`sysctl.conf` 내용 추가/수정:

```
# TIME_WAIT 상태의 소켓 재사용 허용 (클라이언트 측에 유용)
net.ipv4.tcp_tw_reuse = 1
# TIME_WAIT 상태의 소켓을 빠르게 재활용하나, NAT 환경에서 문제 소지 (비활성화 권장)
net.ipv4.tcp_tw_recycle = 0
# FIN_WAIT_2 상태 대기 시간 단축 (기본 60초)
net.ipv4.tcp_fin_timeout = 30
# SYN 백로그 큐 크기 증가 (SYN Flooding 방지 및 연결 설정 안정화)
net.ipv4.tcp_max_syn_backlog = 8192
# 로컬 포트 범위 확장 (더 많은 임시 포트 사용)
net.ipv4.ip_local_port_range = 1024 65535
```

적용 후 `sysctl` 반영:

```bash
sudo sysctl -p
```

이 설정들을 적용한 후, `TIME_WAIT` 커넥션 수는 최대 트래픽 상황에서도 2000개 이내로 안정화되었고, `Address already in use` 에러는 완전히 사라졌습니다. 빌드 시간은 아니지만, 이로 인해 지연되었던 아웃바운드 요청 처리 시간이 평균 1.5초에서 0.2초로 획기적으로 단축되는 효과를 보았습니다.

## 자주 겪는 문제와 해결법

실제로 3-Way Handshake와 4-Way Handshake 과정에서 초보 개발자들이 흔히 겪는 문제와 그 해결법을 정리해봤습니다.

### 1. "Connection refused" 또는 "Connection timed out" 에러

*   **문제 발생**: 클라이언트가 서버에 연결을 시도했지만, 서버가 연결을 거부하거나 응답이 없는 경우.
    ```
    # telnet 192.168.1.100 8080
    Trying 192.168.1.100...
    telnet: connect to address 192.168.1.100: Connection refused
    ```
    또는
    ```
    # curl 192.168.1.100:8080
    curl: (7) Failed to connect to 192.168.1.100 port 8080: Connection timed out
    ```
*   **원인**:
    *   **Connection refused**: 서버의 해당 포트에서 리스닝하는 애플리케이션이 없거나, 방화벽이 연결을 명시적으로 거부하는 경우. (e.g., Nginx, Tomcat 등이 실행 중이지 않음)
    *   **Connection timed out**: 서버가 아예 다운되었거나, 네트워크 경로에 문제가 있거나, 방화벽이 SYN 패킷 자체를 드롭하여 서버가 응답할 수 없는 경우.
*   **해결법**:
    1.  **서버 애플리케이션 확인**: `systemctl status <서비스명>` 또는 `ps -ef | grep <애플리케이션명>`으로 서버 프로세스가 정상적으로 실행 중인지 확인합니다.
    2.  **리스닝 포트 확인**: `netstat -tulnp | grep <포트번호>` 또는 `ss -tulnp | grep <포트번호>`로 서버가 해당 포트에서 리스닝 중인지 확인합니다.
        ```bash
        # 예시: 8080 포트 확인
        netstat -tulnp | grep 8080
        # 출력 예시: tcp        0      0 0.0.0.0:8080            0.0.0.0:*               LISTEN      12345/java
        ```
    3.  **방화벽 확인**: 서버의 방화벽 (`firewalld`, `ufw`, `iptables`)이 해당 포트를 허용하고 있는지 확인합니다.
        ```bash
        # firewalld 예시: 8080 포트 확인
        sudo firewall-cmd --list-ports
        sudo firewall-cmd --add-port=8080/tcp --permanent
        sudo firewall-cmd --reload
        ```
    4.  **네트워크 경로 확인**: `ping`, `traceroute` (`tracert` on Windows) 명령어로 클라이언트와 서버 간의 네트워크 연결 상태를 확인합니다.

### 2. `TIME_WAIT` 상태 포트 고갈로 인한 `Address already in use`

*   **문제 발생**: 고빈도로 아웃바운드 연결을 맺고 끊는 애플리케이션에서 새로운 연결을 맺으려 할 때 발생하는 에러.
    ```
    java.net.BindException: Address already in use: connect
    ```
*   **원인**: 위에서 설명했듯이, `TIME_WAIT` 상태의 소켓이 너무 많아 시스템이 사용할 수 있는 ephemeral port가 고갈되었기 때문입니다.
*   **해결법**:
    *   **`net.ipv4.tcp_tw_reuse = 1` 설정**: `/etc/sysctl.conf`에 이 설정을 추가하고 `sudo sysctl -p`로 적용하여 `TIME_WAIT` 소켓 재사용을 허용합니다. (클라이언트 측에 효과적)
    *   **`net.ipv4.ip_local_port_range` 확장**: 임시 포트 범위를 더 넓게 설정하여 사용할 수 있는 포트 수를 늘립니다. (예: `1024 65535`)
    *   **애플리케이션 설계 개선**: 커넥션 풀을 사용하여 연결을 재사용하고, 불필요한 연결 생성/종료를 줄입니다. 저는 JDBC 커넥션 풀(HikariCP)과 HTTP 클라이언트 풀(Apache HttpClient)을 적극적으로 활용하여 이 문제를 해결했습니다.

### 3. SYN Flood 공격 및 서버 응답 불가

*   **문제 발생**: 서버가 갑자기 느려지거나 응답하지 않으며, `netstat -ant | grep SYN_RECV` 명령어로 확인 시 `SYN_RECV` 상태의 연결이 비정상적으로 많이 쌓이는 경우.
*   **원인**: 악의적인 공격자가 수많은 SYN 패킷을 보내고 ACK 패킷을 보내지 않아, 서버의 연결 대기 큐(`SYN queue`)를 고갈시키는 공격입니다.
*   **해결법**:
    *   **`net.ipv4.tcp_syncookies = 1` 활성화**: `/etc/sysctl.conf`에 설정하면, `SYN queue`가 가득 찼을 때 SYN Cookie 기능을 사용하여 새로운 연결 요청을 처리할 수 있게 합니다.
    *   **`net.ipv4.tcp_max_syn_backlog` 증가**: `SYN queue`의 최대 크기를 늘려 더 많은 SYN 요청을 처리할 수 있도록 합니다.
    *   **방화벽 또는 CDN/WAF 사용**: 서버 앞단에 DDoS 방어 솔루션(Cloudflare, AWS Shield 등)이나 웹 방화벽(WAF)을 두어 비정상적인 트래픽을 필터링합니다.

## 핵심 요약

*   **3-Way Handshake**: 클라이언트와 서버 간 신뢰할 수 있는 TCP 연결을 설정하는 3단계 과정(SYN, SYN-ACK, ACK)으로, 연결 지연 및 거부 문제를 `tcpdump`로 진단하고 방화벽/서비스 상태를 점검하여 해결합니다.
*   **4-Way Handshake**: TCP 연결을 안전하게 종료하는 4단계 과정(FIN, ACK, FIN, ACK)이며, `TIME_WAIT` 상태로 인한 포트 고갈은 `sysctl.conf` 설정을 통해 최적화할 수 있습니다 (`tcp_tw_reuse=1`, `tcp_fin_timeout` 단축).
*   **실전 문제 해결**: `netstat`으로 연결 상태를 모니터링하고, `sysctl` 파라미터 튜닝(`tcp_tw_reuse`, `tcp_fin_timeout`, `tcp_max_syn_backlog`) 및 애플리케이션의 커넥션 풀링을 통해 네트워크 성능 저하와 에러를 효과적으로 방지할 수 있습니다.

### FAQ

### Q1: `TIME_WAIT` 상태를 무조건 줄이는 것이 좋은가요?
A1: 아닙니다. `TIME_WAIT` 상태는 네트워크에 남아있는 지연된 패킷이 다음 연결에 영향을 주지 않도록 보호하는 중요한 역할을 합니다. 무작정 줄이면 "재활용된 포트"로 오래된 패킷이 유입되어 데이터 손상이나 오동작을 유발할 수 있습니다. `tcp_tw_reuse`는 주의해서 사용해야 하며, 서버 측에서는 `tcp_tw_recycle`은 NAT 환경 문제를 일으킬 수 있어 대부분 비활성화하는 것이 좋습니다. 일반적으로 `tcp_fin_timeout`을 30초 정도로 줄이는 것은 큰 문제가 없습니다.

### Q2: 3-Way Handshake가 실패하면 클라이언트와 서버는 어떤 상태가 되나요?
A2: 클라이언트가 SYN을 보냈으나 SYN-ACK를 받지 못하면 `SYN_SENT` 상태에서 일정 시간(운영체제마다 다르지만 보통 몇 초) 대기 후 `Connection timed out` 에러를 발생시키고 연결 시도를 포기합니다. 서버는 SYN을 받으면 `SYN_RECV` 상태가 되지만, 클라이언트로부터 최종 ACK를 받지 못하면 일정 시간 대기 후 해당 연결을 폐기합니다. 이때 `SYN_RECV` 상태의 연결이 너무 많아지면 SYN Flooding 공격으로 이어질 수 있습니다.

### Q3: `FIN_WAIT_1`과 `FIN_WAIT_2`는 어떤 차이가 있나요?
A3: `FIN_WAIT_1`은 클라이언트(또는 먼저 종료를 요청한 측)가 FIN 패킷을 보낸 후 서버로부터 ACK를 기다리는 상태입니다. 이 ACK를 받으면 `FIN_WAIT_2` 상태로 전환됩니다. `FIN_WAIT_2`는 서버가 데이터를 모두 보내고 FIN 패킷을 보내주기를 기다리는 상태입니다. 이 두 상태를 거쳐야 `TIME_WAIT`로 진입할 수 있습니다.
